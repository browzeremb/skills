# Blast radius protocol — scope-feature

Blast radius = the files that depend on (or are depended on by) a file in the change scope. scope-feature collects it **once per feature** so downstream skills (`execute-task`, `code-review`, `write-tests`, `feature-acceptance`) never re-query the dep graph at runtime.

## Why precompute

Every downstream skill that needs to reason about blast radius today re-runs `browzer deps`. That is:

- Repeated work — same files queried 4–6 times across the pipeline.
- Drift bait — the index may shift between phases, leading to inconsistent results.
- Token cost — each phase's LLM ingests duplicate data.

Precomputing once in `EXPLORATION.md` makes the dep snapshot a fixed input the whole pipeline reads.

## Per-file collection

For every `likelyFiles[].path`, run BOTH directions:

```bash
SLUG=$(echo "$PATH" | tr '/' '_')
browzer deps    "$PATH"           --json --save "/tmp/scope-deps-${SLUG}.json"
browzer deps    "$PATH" --reverse --json --save "/tmp/scope-rdeps-${SLUG}.json"
```

Parse the result:

- forward returns `imports[]` → file's forward dependencies
- `--reverse` returns `importedBy[]` → file's reverse importers (the actual blast)

## Top-K cap rule

Caps prevent mermaid diagrams from blowing up on hot-spot files (e.g. a logger module imported by 200 places). The structured frontmatter is also capped, both for token economy and because LLM consumers degrade past ~15 entries per direction (signal-to-noise collapse).

**Default cap: 15 entries per direction per file.**

Algorithm:

1. Apply filter rules (below) over the full result.
2. Sort: test files first (always-kept), then non-generated by score, then alphabetical.
3. Slice to top 15.
4. Record `reverseCount: <pre-truncation>` always. Add `truncatedAt: 15` only when `reverseCount > 15`.

## Filter rules

Apply BEFORE truncation, in order:

1. **Drop co-changing files** — if a reverse importer is itself in `likelyFiles[]`, drop. It's not external blast; it's part of the same change set. The feature graph would otherwise count co-changing files twice.
2. **Always KEEP test files** — regex `__tests__|\.test\.|\.spec\.|_test\.go|_spec\.rb`. These are the signal `write-tests` downstream needs to know which test files cover the changed surface. Never truncate them away even if the per-direction cap fills.
3. **Drop generated artefacts** — `*.gen.*`, `*.pb.go`, `vendor/**`, `dist/**`, `build/**`. Edges into generated code are noise.

## Feature-level union

After every per-file blast is collected, aggregate the feature-wide view:

```yaml
featureBlastRadius:
  reverseUnion: [...]      # union of all likelyFiles[].blastRadius.reverse[].source
                           # minus the self-set of likelyFiles[].path
  reverseCount: N          # full union size BEFORE truncation
  truncatedAt: 50          # OPTIONAL — only when union exceeded the visual cap
```

The union is the surface `feature-acceptance` and `code-review` compare against the actual diff to detect drift between predicted vs implemented scope. The visual cap is larger than the per-file cap (50 vs 15) because the union view is typically reviewed once at gate time, not iteratively.

## Sensitive-scope interaction

Files matching the cross-skill sensitive-path predicate (`../../../references/sensitive-paths.md`) are treated specially in scoping:

1. They still appear in `likelyFiles[]` if a PRD FR touches them (no special exclusion).
2. Their blast radius is collected normally — no cap exemption.
3. They additionally populate `sensitiveScopeHits[]` at the EXPLORATION.md top level with the matched pattern and a one-line reason gloss.

`generate-task` reads `sensitiveScopeHits[]` to require non-empty `task.invariants[]` for any task whose `scope.files[]` intersects this set. Empty `sensitiveScopeHits[]` is valid — most features touch none.

## Performance notes

For a feature with ~30 `likelyFiles`, sequential collection is ~60 `browzer deps` calls (forward + reverse) → ~10–20s wall time on a warm index.

Acceptable because:

- scope-feature runs **once** per feature, not per phase.
- haiku-class dispatch (sub-second per call typical) means even sequential is fast enough.
- Output is persisted to disk; downstream skills read from there.

If wall time exceeds 30s for a single scope-feature run, optimize before scaling out the pattern. Possible future optimizations:

- Parallel `browzer deps` calls via `xargs -P`
- Reuse cached deps if `browzer workspace status` reports the index hasn't changed since the last scope-feature run
- Async dispatch with `--no-wait` and a final join

None of these are needed for v1.

## Edge cases

- **Brand-new file** (no prior version): `forward: []`, `reverse: []`, `reverseCount: 0`. Still record the `blastRadius` block with empty arrays so the YAML shape stays uniform across files.
- **Non-code files** (markdown READMEs, JSON config, images, CSV fixtures): `browzer deps <path>` exits non-zero with `Error: Not found.` because the dep graph only tracks code imports. Treat this as a legitimate empty blast radius: record `forward: []`, `reverse: []`, `reverseCount: 0`, and continue. Do NOT halt the scope-feature run. Markdown files under `docs/` are the canonical case.
- **Thin / empty edges on a stale index**: when preflight reports the index is stale AND `browzer deps --reverse <file>` returns minimal or no edges for a file you can see has importers via `grep`, fall back to `grep -rln "<basename without extension>" --include='*.{ts,tsx,js,mjs,go,py}' .` for ground truth. Populate `reverse[]` from the grep output (kind: `imported-by`, via: empty) and add a one-line entry to `assumptions[]` naming the fallback ("blast radius for `<path>` derived from grep; index appears stale relative to source"). The operator can then decide whether to re-index before the next phase.
- **File deleted by this feature**: scope-feature SHOULD NOT list it in `likelyFiles[]` (the PRD typically describes the new state). If it must be tracked, record under `assumptions[]` instead.
- **File renamed**: treat as both new file and old file (if the rename is part of the change scope). Blast radius is computed against the **old** path because the dep graph at scope-feature run time still references the old name. After execute-task lands the rename, the dep graph will refresh.
- **Symlink / re-export barrel**: `browzer deps` follows imports literally. If `index.ts` re-exports from `foo.ts`, both edges appear. This is correct — the import edge is real even if it feels "transparent" to the developer.
- **Generated file in `likelyFiles[]`**: rare but possible (e.g. when a PRD covers regenerating the schema artefact). The filter rules apply to BLAST entries, not to `likelyFiles[]` itself — generated files in scope are kept verbatim with their blast radius collected like any other.
