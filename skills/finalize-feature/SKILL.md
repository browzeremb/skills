You write the human-readable `docs/browzer/<feat>/README.md` for a completed feature. You do NOT implement code. You read workflow state and produce a committable summary.

## Read context

```
!`browzer get-step FEATURE_ACCEPTANCE --id "$ARGUMENTS" 2>/dev/null || echo "(no FEATURE_ACCEPTANCE step — run after feature-acceptance)"`
```

```
!`browzer get-step ORIGINAL_REQUEST --id "$ARGUMENTS" 2>/dev/null || echo "(no ORIGINAL_REQUEST — check feature id)"`
```

```
!`browzer get-step CONFIG --id "$ARGUMENTS" 2>/dev/null || echo "(no CONFIG)"`
```

```
!`browzer get-step PRD --id "$ARGUMENTS" 2>/dev/null || echo "(no PRD step)"`
```

```
!`browzer get-step TASKS_MANIFEST --id "$ARGUMENTS" 2>/dev/null || echo "(no TASKS_MANIFEST step)"`
```

`$ARGUMENTS` is the feature id (e.g. `feat-20260507-my-feature`); it is the directory name under `docs/browzer/`.

## Process

1. Collect all phase statuses by reading each completed step via `browzer get-step <PHASE> --id "$ARGUMENTS"`.
2. Extract from PRD: feature title, deferred / out-of-scope items, deploy notes, out-of-band gates.
3. Extract from TASKS_MANIFEST: list of TASK_NN ids and their scopes.
4. Extract from ORIGINAL_REQUEST: verbatim operator brief.
5. Write `docs/browzer/<feat>/README.md` (NOT inside `staging/`) with the shape below.
6. Return the one-line output contract.

## Idempotency

The README is written ONCE per pipeline run. If `<feat>/README.md` already exists from a prior partial run, OVERWRITE it (idempotent). Do NOT append. Write unconditionally — the `Write` tool overwrites any prior README at the same path. Re-running is safe.

When assembling sections from phase data (deferred items, deploy notes, task scopes, out-of-band gates), perform a SINGLE union+dedupe pass over the source phases — do NOT loop per phase emitting the same section repeatedly. For example, deploy notes and deferred items may appear in PRD, FEATURE_ACCEPTANCE, or task receipts; collect them into one set keyed by content, then render each entry exactly once.

## Canonical H2 sections (closed set)

The README MUST use exactly the following H2 headings, in this order, each emitted **at most once**:

1. `## Original request`
2. `## Phase summary`
3. `## Tasks`
4. `## Deferred actions / follow-ups`
5. `## Deploy notes`
6. `## What was NOT verified`
7. `## Blast-radius receipts`

Rules:

- An H2 MUST match one of the seven headings above verbatim (case, punctuation, and wording). Near-duplicates with re-worded titles (e.g. `## Deferred / Out-of-Scope`, `## Deploy Notes`, `## Phases`) are forbidden — they are the source of the dedup-key drift this rule exists to close.
- Each heading appears at most once. Render order MUST follow the list above.
- Optional sections with no content MUST be **omitted entirely** — preferred over leaving an empty section or stub text like "None.".
- Adding a NEW H2 not in this list requires updating this SKILL.md (this section) FIRST, in the same change. Skills MUST NOT introduce ad-hoc H2 headings at write time.
- The `## Phase summary` heading carries the gate-status table (the same content the legacy `## Phases` section held). The `## Original request` body is the verbatim ORIGINAL_REQUEST blockquote.

The "README shape" example above is illustrative for content layout; the headings listed in this section are authoritative when they conflict.

## Surface boundary

finalize-feature MUST NOT print the closure block to chat — that surface belongs to the orchestrator. The README content MAY duplicate orchestrator closure in the README file (file vs. chat are different surfaces), but the chat closure runs once via the orchestrator. This skill's only chat output is the one-line cursor in the output contract below.

## Staging skip

Do NOT write to `staging/` for the README. Write directly to `docs/browzer/<feat>/README.md`.
The `staging/` path is reserved for workflow phase artifacts consumed by the autosave hook; README lives at the feature root.
